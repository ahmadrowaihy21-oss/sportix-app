# SPORTIX ATHLETE — تطوير وتغطية MVP

المراجعة: 12 نوفمبر 2026، بتوقيت الرياض. المصدر الأساسي `main@62011704c6e56d732948a66dbc1cbfed4f211e38`.

**الحكم:** أصبحت رحلة الرياضي والشريك قابلة للتجربة عبر ثمانية أنواع خدمات، واجتازت اختبارات المنطق والمتصفح على الجوال والكمبيوتر في نسختي التطوير والبناء، مع كود خادم يحمي الوصول والسعة. هذا لا يثبت اكتمال منصة إنتاجية بكل الخدمات. المصادقة الفعلية ومزودو الدفع والربط الخارجي واختبارات حسابات حقيقية تبقى بوابات إطلاق. التغييرات في PR#6، ولم تُدمج أو تُنشر إلى الإنتاج ضمن هذه المراجعة.

## ما تغيّر

- `/marketplace` و`/services`: كتالوج موحد بالعربية والإنجليزية، بحث حسب الخدمة والمدينة، تصفية، سعة وأسعار ومواعيد الرياض، موافقة قبل الطلب، كمية المنتجات، متابعة وإلغاء وتقييم بعد الإتمام فقط.
- `/partners`: إنشاء عرض كمسودة → إرسال للمراجعة → اعتماد من مراجع مختلف → نشر/إيقاف؛ استقبال الطلب → قبول/رفض → إتمام. تبديل الأدوار موجود في المحاكاة فقط.
- GO SPORTIX → سجل SPORT ID الخاص → منشور المجتمع بموافقة صريحة. الافتراضي خاص، والمقاييس تحتاج موافقة منفصلة، وسحب المشاركة يزيل الإسقاط. لا تمنح المحاكاة اعتمادًا أو مكافآت.
- سجل أنشطة اصطناعي قابل للاستعادة بعد تحديث الصفحة، دون حفظ صور أو فيديو أو موقع أو بيانات صحية. الجلسة الجارية لا تُستعاد؛ خطأ التخزين يظهر للمستخدم.
- سجل طلبات مستقل في SPORT ID. لا يتحول إكمال خدمة إلى أداء رياضي موثق.
- حفظ سجل خدمات التجربة في المتصفح، وإعادة تطبيق الأوامر مع التحقق عند التحميل. تستخدم الكتابة Web Locks عندما تتوفر؛ هذه ليست قاعدة بيانات متعددة المستخدمين.
- حجب نجاح الشراء/القسيمة القديم من الواجهة، وإزالة ادعاء اتصال GPS/Health/Watch التلقائي، وعدم منح أذونات فعلية عند تخطي الترحيب.
- معاينة تغطية نقاط متوازنة محاسبيًا: السعر الأصلي = تغطية SPORTIX + حصة الرياضي. سياسة `market-sandbox-v1` (0.10 ريال/نقطة، 30%) اختبار فقط، لا تخصم نقاطًا ولا تعتمد خصمًا أو تسوية.

## دورة الطلب وقواعدها

الحجز المؤقت لمدة تصل إلى 15 دقيقة. `REQUESTED → ACCEPTED → COMPLETED`، مع `CANCELLED` و`REJECTED`، أو `EXPIRED` عند انتهاء المهلة قبل القبول. الإلغاء/الرفض/الانتهاء يحرر السعة مرة واحدة؛ لا يعيد إكمال الخدمة السعة لأن العرض يمثل مخزونًا أو موعدًا محددًا. لا يستطيع الرياضي إتمام الخدمة أو تقييمها قبل اكتمالها. قبول الطلب ليس إيصال دفع. قبول موعد لا يمكن أن يحدث بعد بدايته.

في التشغيل الفعلي، يمنع الخادم إتمام خدمة مدفوعة أو إصدار منتج/قسيمة/اشتراك بدون موصل موثوق. لا يوجد أمر من العميل لتعيين `paid` أو خصم النقاط. يُسمح بإتمام خدمة مجانية غير تجارية بعد بدايتها فقط، وبصلاحية الشريك.

## مسار الخادم وحدوده

`api.ts` يستخدم المصادقة وحماية الأصل الموجودة في التطبيق. لا يقبل معرف مستخدم من الحمولة. `context.server.ts` يتطلب `SPORTIX_SERVICES_ENABLED=true` وقاعدة بيانات `DATABASE_URL` وهوية ليست dev-user أو spx_test. يلزم تهيئة حساب وعضوية معتمدة؛ لا يوجد endpoint يمنح صلاحيات للشريك بنفسه.

تخزن `sportix_service_workspaces` حالة المؤسسة مع إصدار. عملية SQL واحدة مشروطة بالإصدار تحفظ المخزون والطلب والإيصال وسجل التدقيق معًا. يعاد التحقق بعد التنافس، حتى 12 محاولة. حسابات وعضويات المؤسسة في جدولين منفصلين. لا تُرسل إيصالات منع التكرار أو هويات المراجعين إلى الرياضي.

الواجهة التشغيلية مهيأة لمؤسسة واحدة يحددها `VITE_SPORTIX_PARTNER_TENANT`؛ الكتالوج متعدد المؤسسات، onboarding، pagination وأرشفة أكثر من 10,000 أمر لكل مساحة عمل تحتاج تطويرًا إضافيًا. لم يُنفذ اتصال HTTP بمختبر الشركاء المنفصل في PR#2؛ هذا تنفيذ داخل تطبيق ATHLETE يعيد استخدام المفاهيم نفسها، وليس إثبات ربط النظامين.

## نتائج التحقق

- تثبيت نظيف مطابق لـ`package-lock.json` بواسطة `npm ci --ignore-scripts` محليًا و`npm ci` في GitHub Actions نجح، دون تغيير الاعتماديات.
- اختبارات ATHLETE: 62 ناجحًا، تشمل الخصوصية والهوية وعدم مضاعفة السجلات واستعادة السجل وسحب المنشور بعد إعادة التحميل.
- اختبارات خدمات الشركاء/النقاط/SQL: 25 ناجحًا، منها 30 متنافسًا على مكان واحد مع نجاح واحد، وإعادة الأوامر دون تكرار حجز/إلغاء، واستعادة بيانات PGlite من dump، ورفض العضويات المزورة/المعطلة، وثبات معادلة التغطية عبر 1000 سعر صحيح.
- اختبارات النطاق الحالية: 60 ناجحًا، منها اختبارات الأكاديمية الخمسة. مجموع الاختبارات الفريدة لهذه المجموعات: 147.
- TypeScript للتطبيق والاختبارات وبناء Netlify المحلي: ناجحان.
- مجموعة scripts الأصلية: توجد 14 مشكلة سابقة مرتبطة بملفات `.grok` غير الموجودة وتوقعات علامة قالب مختلفة. لا ينبغي وصف المستودع كله بأنه أخضر. عُدّل اختبار خطة migrations حتى يختبر عزل auth بدل افتراض عدم وجود أي migration للتطبيق.
- فحص Chromium في GitHub Actions: ناجح على الكود `9b3263e5ff82648fd76b385fd094271a62f5557a`، بعد تعذر تشغيل Chromium محليًا. شمل الموافقة قبل الطلب، الحفظ بعد التحديث، قبول الشريك وإتمامه، تقييم الرياضي، الإلغاء، وظهور تاريخ الطلبات في SPORT ID. يستخدم بيانات اصطناعية وحالة متصفح فعلية، دون حقن نتائج أو اعتراض الشبكة.
- ستة مسارات (`/services`، `/partners`، `/communities`، `/go-sportix`، `/sport-id`، `/marketplace`) عُرضت على مقاسي 390×844 و1280×900، في التطوير والبناء: لا تجاوز أفقي ولا أخطاء page/console. حُفظت 24 لقطة وملفا نتائج داخل artifact باسم `athlete-browser-evidence`. روجعت لقطات الخدمات للجوال والكمبيوتر ومساحة الشريك للجوال بصريًا.
- أصلح فحص المتصفح تهيئة الترحيب واختلاف SSR، وتفعيل تبويب الطلبات قبل جاهزية بياناته، ورابط CSS غير الموجود في نسخة البناء. تعاد هذه الرحلات تلقائيًا عند تعديل كود المسارات في PR.
- اختبار قاعدة البيانات يستخدم PGlite محليًا، وليس PostgreSQL منشورًا متعدد العمليات. لم نختبر جلسات شخصين حقيقيين أو دفعًا أو مستودع تاجر أو أجهزة/كاميرات حقيقية.

## إعدادات التفعيل قبل الإطلاق

1. فحص CI والجوال/الكمبيوتر ناجح لهذه النسخة؛ تبقى مراجعة التغييرات وإغلاق فشل القالب المناسب لبوابة الإصدار.
2. تفعيل مزود الهوية الحالي وربط جلساته، تشغيل migrations، إنشاء حسابات وعضويات معتمدة ومساحة operational فارغة؛ لا تستخدم fixtures الإنتاجية.
3. ضبط المتغيرات السابقة على بيئة معاينة مصرح بها أولًا. أسرار الخادم لا تحمل بادئة VITE.
4. اختبار حساب رياضي ومؤسستين ومراجع، إلغاء العضويات، انقطاع الشبكة، إعادة المحاولة، وتزامن عمليات متعددة على PostgreSQL فعلي.
5. توصيل الكتالوج الموحد/Rooms/مخزون المؤسسة، الدفع وwebhooks ودفتر النقاط والاسترجاع؛ ثم اختبارات قبول منفصلة لكل موصل.
