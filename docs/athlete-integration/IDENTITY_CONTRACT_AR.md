# SPORTIX USER ID — عقد الهوية المقترح v1

الحالة: مقترح قابل للمراجعة، مع مخطط تحقق منفذ واختبارات محلية. لا توجد خدمة هوية إنتاجية جديدة في هذه الحزمة.

## المعنى والملكية

- `sportixUserId`: معرف داخلي ثابت غير دال على الشخص، بصيغة `spx_u_<UUID>`. يصدره خادم الهوية مرة واحدة؛ لا يستخرج من البريد أو الجوال أو رقم الهوية أو اسم العرض.
- الربط بين الهوية المصادق عليها وSPORTIX USER ID يتم في الخادم عبر جدول `auth_subjects` بقيد فريد `(issuer, subject)`. تغيير البريد لا ينشئ رياضيًا جديدًا. ربط حسابي دخول يتطلب إثبات ملكية كليهما؛ لا دمج تلقائي اعتمادًا على تطابق البريد.
- `publicProfileId`: معرف عام مستقل، وليس نسخة من المعرف الداخلي؛ المنشور العام لا يتضمن معرّفات المصادقة أو بيانات الاتصال.
- `tenantId`: نطاق المؤسسة للخدمات والشركاء، وليس بديلًا عن هوية الرياضي. يستخرج الخادم عضوية المؤسسة من جلسة موثوقة. لا يقبل دورًا أو مؤسسة من جسم الطلب باعتبارهما صلاحية.
- `spx_test_*`: نطاق مختلف مقصور على الاختبارات. الشخصية الحالية `spx_test_athlete_001` اصطناعية. `yousef` مجرد alias للعرض في مكونات المجتمع الحالية. لا يمثل الحساب المتصل ولا يُرحّل إلى الإنتاج.

## الجلسة والربط الحالي

توجد بنية Better Auth في `src/lib/auth/`، لكن مسارات ATHLETE الأربعة لا تستدعي حارس هوية خادمي ولا تتبادل سجلاتها مع خدمة بيانات. `AuthProvider` غلاف passthrough. `requireUserId` قد يعيد `dev-user` عند تعطيل المصادقة دون قاعدة بيانات؛ يجب رفض هذا البديل في أي معاملة تشغيلية. ملفات مسارات `/api/auth/*` غير موجودة ضمن النسخة المقروءة رغم وجود المكتبات الداعمة. تعليقات القالب التي تقول إن auth معطل لا تكفي: `.grok/app-env.json` غائب في snapshot، والعميل يعتبر المصادقة مفعلة إلا عند القيمة النصية `false`.

لا توصل هذه الحزمة الحالة الاصطناعية بحساب المستخدم الحقيقي. لا يجري استيراد جلسة أو بيانات أشخاص. للمسار التشغيلي التالي: تحقّق من جلسة Better Auth في الخادم → رفض signed-out وdev fallback والحساب الموقوف → البحث عن mapping فريد → سياق طلب داخلي يحوي SPORTIX USER ID → تطبيق صلاحية كل مورد في الخادم.

## الموافقات والخصوصية

المشاركة خاصة افتراضيًا لكل نشاط. الموافقة على النشر مستقلة عن حفظ SPORT ID، وموافقة عرض المقاييس مستقلة عن الجمهور. الحقول المحفوظة: audience، shareMetrics، policyVersion، consentVersion، updatedAt. عند سحبها أو تضييقها يعاد حساب الإسقاط وتزال النسخة المشتركة فورًا محليًا. لا تشارك الصورة أو الموقع الدقيق أو الصحة حتى عند مشاركة المقاييس. النتيجة المحاكية تظهر `verified:false` ولا تصبح اعتمادًا حقيقيًا.

في الخادم يجب إعادة تقييم الموافقة عند كل قراءة، وفي الروابط المباشرة والبحث والإشعارات وملفات cache وCDN؛ حذف/إبطال الإسقاطات والروابط الموقعة القديمة، مع retention منفصل للأدلة وسجل الموافقة. علاقة الأصدقاء تأتي من خدمة المجتمع، لا boolean يرسله العميل. حارس العرض في المتصفح تحسين عرض فقط وليس حدًا أمنيًا. القاصر محجوب عن المشاركة خارج الخاص في المختبر حتى تنفيذ سياسة ولي الأمر والمراجعة القانونية المطلوبة.

في SPORT ID تظهر سجلات الربط الخاصة في عرض owner فقط، ولا تظهر في public/professional. تبديل عرض واجهة المستخدم ليس مصادقة أو تفويضًا خادميًا. إشعارات الطرف الثالث والإعلانات ومشاركة الشركاء تحتاج موافقات منفصلة ولا تستنتج من موافقة منشور نشاط.

## مصدر الحقيقة والتحقق

المسار المحلي: CREATED → SUBMITTED → SIMULATED_COMPLETED أو REVIEW_REQUIRED أو INSUFFICIENT_EVIDENCE. إعادة المحاولة بعد نقص الأدلة مسموحة بإصدار جديد. لا يوجد أمر عميل ينتج VERIFIED. Cycling يظل REVIEW_REQUIRED حتى لو اختير نجاح المحاكاة.

المسار التشغيلي المقترح: CREATED → SUBMITTED → VERIFYING → VERIFIED_COMPLETED / REVIEW_REQUIRED / REJECTED، بواسطة عامل تحقق أو مراجع مخول فقط. تحفظ نسخة قواعد التحقق ومرجع الأدلة ووقت ومصدر القرار. مصادقة المنفذ وتوقيع الحدث وعزل المالك لا تتحقق باجتياز JSON Schema وحده. حقل `provenance` الذي يرسله العميل ليس إثبات ثقة.

## الاتساق والهوية التجارية

في الإنتاج تنفذ نتيجة التحقق + سجل SPORT ID + outbox ضمن معاملة واحدة؛ المستهلكون يزيلون التكرار بمفتاح `(consumer,eventId)`. تستخدم optimistic concurrency وexpectedVersion، وتخزن نتيجة idempotency مع بصمة payload ضمن نطاق المالك. الطلب المكرر بنفس المحتوى يعيد النتيجة، والمحتوى المختلف يعطي 409. سحب الموافقة حدث عالي الأولوية ويمنع إنشاء منشور من حدث نشاط متأخر.

طلبات المتجر تستخدم مبالغ صحيحة بالهللات (`priceMinor`) وعملة محددة. يحسب الخادم السعر والضرائب والإجمالي والخصم بعد قراءة إصدار العرض والمخزون؛ لا يعتمد `amountMinorPreview` أو `requestedPoints` من العميل. لم نعتمد أي معادلة «نقطة = ريال».

حجز مخزون ذرّي بمهلة زمنية، ثم دفع عبر مزود موثوق مع webhook موثّق ومطابقة المبلغ/العملة/الطلب/المالك وعدم تكرار الحدث. إصدار القسائم وصرفها وخصم النقاط وتوليد المكافآت تتم بمعاملات خادمية مستقلة وفق القواعد. إيصال sandbox، أو `outcome:success`، أو علم `synthetic:false` داخل payload لا يعتمد عملية. لم تُضف في هذه الحزمة وسيلة لتجاوز الحجب.

## البيانات الحالية والترحيل

لا ترحيل من mock أو Zustand أو sessionStorage إلى الحسابات التشغيلية. تنشأ قاعدة التشغيل فارغة، وتُستورد لاحقًا بيانات مصرح بها بعد التحقق من الملكية والموافقة. عند تسجيل الخروج/تبديل المستخدم في التنفيذ التشغيلي يجب مسح جميع caches والمتاجر المحلية وإلغاء الطلبات الجارية قبل تحميل بيانات الهوية الجديدة. إدارة ذلك عبر جلسة حقيقية لم تنفذ هنا.
